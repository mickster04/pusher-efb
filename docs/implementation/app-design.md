# App design: Plan and Push tabs

Replaces the earlier feasibility app, which is on the `spikes-app` branch; what they proved is in `feasibility-findings.md`, `efb-platform-notes.md` and `wasm-taxi.md`.

## Plan tab (built; browser harness and unit tests only, not yet run in the sim)

- **Plan model** (`src/planning/plan.js`, `PS.plan`): the user's pins in the original app's waypoint shape (`id, label, lat, lon, seq, terminal, headingDeg, headingUser, drive, leadInM`). The last pin is the end pin. A pin's heading is Auto (the planner works out the nose it ends with) until the user rotates it, when it becomes a heading the route must arrive along. `evaluate(origin)` plans the route from the aircraft and returns the legs (push back or forward), the line to draw, the nose at each pin, any warnings, and any turnaround pin the planner added. It is cached until the pins or the aircraft change.
- **Planner** (`src/planning/route-planner.js`, `PS.planner`): a port of the planner section of the original `apps/windows/src/mapGeo.ts`, which mirrors the bridge's `FilletPath` (turn radius 40 m, arcs between straight legs, a straight start along the aircraft's axis, forward when a leg is within 70 degrees of the nose on the first leg and 90 later, hairpin detection and turnaround pins, `segmentWarning`). `withAutoOrientation` is not ported (the suggester does not use it).
- **Suggester** (`src/planning/push-suggest.js`, `PS.suggest`): a port of the original `taxiSuggest.ts`, built on the planner. Checked against the original TypeScript run in Node (`test/tools/make-suggest-golden.mjs` regenerates `test/fixtures/suggest-golden.json`); the option titles agree on the recorded scenarios, with a few equal-cost ties decided differently by float noise. One deliberate difference: the tail-axis hit has a small tolerance, so a line passing exactly through the joint between two taxiway stretches is not lost to rounding.
- **UI** (`src/pages/plan.js`): canvas plot, directional pins (an aircraft marker rotated to the nose heading) with a selection ring and a draggable heading handle, the route summary and warnings, the suggestion list ("Use as my plan"), the pin list, and the refresh diagnostics panel from the Map spike. Pin drag and tap use mouse events; whether the EFB's touch input produces them is untested.
- **Differences from the original UI:** no first-click-is-last-pin setting (pins are added in order and the last is the end pin); the heading handle is a fixed distance behind the tail on screen, not 22 m on the ground; no lead-in handle yet (`leadInM` is carried but cannot be edited).

## What the sim showed about the Plan tab (Nov 2026, from the owner's logs)

- **Canvas repaint:** the sim does not repaint a canvas by itself: draws happened (diagnostics: steady draws, no errors) but the plot only appeared after the page was scrolled away and back. Nudging after each draw fixes it; the **style** nudge (alternate the canvas opacity by 0.1%) was reported to work, so it is the default. The Repaint button cycles style, all (reallocate canvas + one-pixel readback + style), resize, flush and off, for testing.
- **Input:** only mouse events reach the canvas (`mousedown`, `mousemove` while pressed, `mouseup`, `click`); no touch or pointer events were seen. Drags work.
- **Tap position was off by about 100 m north** when computed from `clientX/Y` against `getBoundingClientRect()`. The tap is now computed from `offsetX/offsetY` (relative to the canvas), with a **five-spot calibration** (four corners and the middle) that fits scale and shift per axis for both measures, picks the better, applies it and saves it. The first ten taps and every calibration tap are logged with all the raw numbers (`press raw: client ... offset ... canvas rect ...`), and a cyan cross shows where the app thinks a tap landed. If this proves unnecessary once the offset method is confirmed, it can go.
- **Finding the heading handle** was hard (about 12 screen pixels to hit on a plot shown at 3/4 size): the handle is now larger and further behind the pin, and the press zone is 36 canvas pixels plus the stem. A white **cursor cross** follows the pointer to show live where the page thinks it is (log lines `hover raw: ...` give the numbers); if it is not under the real cursor, taps are off.
- **Tap error that grows away from the top-left corner** (reported from the sim) means a wrong scale, not just a shift, and only the first of the five calibration targets was noticed (the others were thin grey, two below the fold and one behind the aircraft). The page now logs the display environment on opening and on **Scan canvas** (window and screen sizes, devicePixelRatio, and every ancestor's transform, zoom and overflow), finds the canvas's real hit region with `document.elementFromPoint` (a third measure, H, only trusted when the whole canvas is in view: the scan reports which edge is cut off otherwise), and draws three crosses at the pointer: R (client position against `getBoundingClientRect`), O (`offsetX/offsetY`) and H (hit-test box). Whichever stays under the real cursor in the corners is right; **Use R / Use O / Use H** picks it. Calibration targets are now bold cyan and the fifth moved off the aircraft.
- **The plot must not be scaled by CSS** (found from the owner's observations: all three tap measures agreed with each other, the error grew with distance from the canvas's top-left corner, and only the first of the calibration targets was visible). The most likely cause is that the sim draws a canvas at its full backing size and does not scale it down to a smaller CSS box, so only the top-left part showed and every tap was converted with a scale the drawing did not have. The canvas is now sized from the space available (`fitCanvas`: width up to 900, a 5:3 shape, short enough to leave the whole plot on screen) and its CSS size is set to exactly its backing size in pixels, so nothing is scaled. Saved tap calibrations from earlier builds are discarded (storage key `pushplanner.tapcal3`). Not yet confirmed in the sim.
- **Moving the map:** dragging empty map (not a pin or its handle) pans it, so you can look across the airport without zooming out; **Recentre** returns it to the aircraft, and the info line says how far it has been moved. A click without a drag still drops a pin.
- **Tightest turn:** the plan tightens its turn radius from 40 m down to a setting (default 26 m) where a corner is too cramped; see `pusher-internals.md`.
- **Suggestions:** choosing one makes it the plan and removes any pins placed by hand that are not part of it; adding, moving or rotating a pin afterwards drops the suggestion highlight. Compass-pointing options, cramped arcs (tightest arc under 32 m or a start more than 45 degrees off the axis) and lanes or links (when a named taxiway has an option) are left out.

## Push tab (built; checked against a fake sim, not yet in the real sim)

Files: `src/push/tug.js` (`PS.brake`, `PS.tug`), `src/push/follow.js` (`PS.follow`), `src/push/push.js` (`PS.push`), `src/pages/push.js` (the tab).

- **Flow.** Start does it all: attach the tug if it is not on (hold with `PUSHBACK WAIT`, `TOGGLE_PUSHBACK`, wait for `PUSHBACK ATTACHED`, as the original and the earlier tug test did), check the parking brake and wait for it to be off, settle (2.5 s after attaching; the original waits longer on a fresh attach, not yet tuned), then drive. The tug can also be called and dismissed on its own.
- **Parking brake** (`PS.brake`, from the original's `SimService.cs`): "set" is read from `BRAKE PARKING POSITION` as a bool, a 0 to 1 position, a percent or a 16k position, plus the first of the known lever variables that reads set (FlyByWire, Fenix and others leave the simvar at 0). Release writes the simvar both ways and every known lever variable, then, if it is still set, sends `PARKING_BRAKES`. It is enforced at the start (the push waits, with a popup offering to release it) and during the push (a brake set mid-push stops the tug and it carries on when released).
- **Driving.** Each tick (50 ms) writes `PUSHBACK WAIT` 0, `VELOCITY BODY Y` 0, `ROTATION VELOCITY BODY X` 0, `VELOCITY BODY Z` (ft/s, negative = reverse) and `ROTATION VELOCITY BODY Y` (rad/s, **positive turns the nose right**, from the original's rotation sign and the earlier test). Speed ramps at 14 ft/s per second and turn at 5 deg/s per second. Default cruise is 50% of the original's top speed (speed factor 25, 5 ft/s forward, 75% of that in reverse), with the speed chosen from the path itself (`buildProfile` in `src/push/follow.js`): top speed on straights; in a curve a cap of about 3.0 ft/s forward / 2.75 reverse, scaled down for radii under 40 m; braked early enough (0.35 m/s^2) to be at the curve speed when the curve starts and at a crawl at the end of each leg, and eased back up (0.5 m/s^2) afterwards. The Push tab shows why the speed is what it is. Changing the cruise speed mid-push rebuilds the profile (`setCruise`).
- **Follower** (`PS.follow`): pure pursuit as in the original (look-ahead 8 to 10 m, curvature `2 sin(alpha) / distance`, rotation setting = curvature x 30.48, steering limits 2.0 forward and 1.8 reverse). It allows for the tug's measured response (the nose turns at 2.3 x the command minus 0.30 deg/s). Not ported from the original: the learned yaw calibration (B7), the straight-stretch slack, and the end-pin creep with a time limit. Each leg is driven in one direction; between legs it stops, holds one second and reverses (a cusp). Watchdogs: more than 15 m off the path for 3 s, or no progress along the path for 8 s, stop the push.
- **Tested** (`test/follow.test.mjs`, `test/push.test.mjs`): the follower against a simulated tug (within 0.5 m of the line, ending within 0.8 m, straight, arc, cusp, sluggish tug, tightened arc), and the whole state machine against a fake sim (attach, wait for the brake, release, drive, finish; the tug detached mid-push; brake set mid-push; pause and resume; refusing to start; closing the app). The harness also runs it end to end with the Push tab.
- **Not verified in the sim** (and what to watch in the log's `push` lines each second: speed target, ramped and read back, yaw target, ramped and measured, off-path distance): that the rotation sign (confirmed on the Fenix A320) and the 2.3/0.30 response (fitted from the first real pushes) hold on other aircraft; that the aircraft follows the planned arcs at these speeds; whether the settle time is enough; brake release on each aircraft; and that nothing else (the aircraft's own systems, the sim's tug logic) fights the writes.
- **Safety.** Nothing is written unless the tug is attached. The push stops at once (zero written, no easing) if the app is closed (going to another EFB app only pauses it: its timers keep running, so the push carries on) or its timer stalls for over 1.2 s, the aircraft leaves the ground, the position cannot be read, or the follower reports the path is lost or the aircraft is not moving. If the sim detaches the tug the app stops writing altogether (writing velocity to a free aircraft shoves it). A push is also ended after 20 minutes.
- **Next** (from `docs/efb-requirements.md`): the in-sim turn test to measure the real minimum radius and the yaw response (B7), the learned yaw calibration, return to gate (D5), ground services (G), traffic watch (F), saved plans and settings (D6, J), and popups that reach a pilot looking away from the tablet (I1).


## Tabs and settings

- **Plan**: map, then either the Suggested pushes list or the Custom pins list (one at a time; placing/moving/rotating a pin shows the pins, choosing a suggestion shows the suggestions). A one-line route summary points to the Push tab for details.
- **Push**: controls, the Route panel (radius, legs, warnings), progress, map, log.
- **Settings** (`src/core/settings.js`, localStorage `pushplanner.settings`): tightest turn, snap pins to taxiway on/off, which Plan list opens first.
- Plan warnings are logged on the `plan` channel (`WARNING ...` plus the pins behind it) whenever the route changes.

## Finishing and returning to the gate

- When a push finishes, the pins are deleted (the finished route stays on the Push map until the next push).
- If the push planned without a warning, **Return to gate** (Push tab, and on the "Push finished" popup) drives the same route back: legs reversed in order and direction, no input. It needs the aircraft to be within 20 m of where the push ended, on the ground; like any push it attaches the tug if needed and waits for the parking brake to be off. A push that is stopped part way (by you, the brake, or the sim taking the tug) gets a return over the ground it covered, as far as it got; a return that is stopped keeps what is left of the way back. The option goes when a return finishes, when a new push starts, or when the aircraft is moved away.

## Layout, buttons and settings (latest)

- **Landscape/portrait**: the shell compares its own width and height (checked every second, on resize and each frame) and adds `ps-landscape`; the Plan and Push pages are then two flex columns (map left, lists/controls right). No grid or calc(): the sim's browser is old.
- **Help**: the long explanations are in a "?" card (`PS.ui.help`) shown on hover (tap on touch) instead of on the page.
- **Push tab buttons** are always shown and disabled when unusable. Main row: Start push (which becomes Finish push when the push is done: they are never both needed), Return to gate, Pause/Resume, STOP. Lesser row: Call/Dismiss the tug, Set/Release the brake. Start calls the tug and releases the brake itself (skipping what the pilot already did); Finish sets the brake and dismisses the tug (skipping what is already done). The route panel is gone from the Push tab: warnings are on the Plan tab and the pushing map shows the route being driven.
- **Settings** also holds the log, the snap reach, and the top/bottom margins that keep this app clear of the EFB's own header and bottom bar.
- **Suggestions** plan with the same radius ladder as pins (the usual 40 m, then tighter down to the Settings tightest turn).

## Themes and icons

- **Themes** (`src/ui/theme.js`): a palette of named roles (page, map and route colours). `styles.css` is a template with `@role@` tokens, rebuilt and swapped into the style element when the theme changes (the sim's browser has no CSS variables); the map drawing asks `PS.theme.c('role')`. Shades the stylesheet needs are mixed from the roles, so a custom palette stays consistent. 17 presets: Push Planner, High contrast, Night (red), Daylight, and airline-inspired ones (Delta, British Airways, Lufthansa, Air New Zealand, Eurowings, Qantas, Emirates, KLM, Singapore Airlines, Air France, Ryanair, easyJet, Qatar Airways; approximate colours, not official). The choice and the user's own colours are saved in localStorage `pushplanner.theme`.
- **Settings > Colours** (`src/ui/colours.js`): a Themes tab of cards that preview each palette, and a My colours tab to set every role (tap a swatch for a palette, or type a hex). A theme can be copied as JSON and pasted back, which is the hook for sharing themes.
- **Icons**: `PS.icon(name)` draws inline SVG (`PS.ICONS`, 24 x 24 grid, current text colour), used by `ui.iconButton`. The sim's fonts lack many symbols (arrows, degree sign on buttons), so use these or plain words.

## Theme files

- The presets live as JSON in `src/themes/` (`index.json` gives the order). The build embeds them in the bundle (so a theme always works) and copies them to `PackageSources/PushPlanner/themes/`, which the package ships to `html_ui/efb_ui/efb_apps/PushPlanner/themes/`.
- At start-up the app reads `themes/index.json` and each file it lists with `XMLHttpRequest`, from `coui://html_ui/efb_ui/efb_apps/PushPlanner/themes/`. A file replaces the built-in theme with the same id, or adds a new one. A bad file is skipped and reported on Settings and in the `theme` log lines.
- A theme file is grouped: `{ "id", "name", "note", "page": { "surface": {bg, bgDeep, panel, border, input}, "text": {...}, "controls": {...}, "status": {...} }, "map": { "surface": {...}, "paths": { "runway": {colour, width}, "taxiway": {colour, width} (named), "unnamed": {colour, width} }, "labels": {size, gap}, "route": {...}, "markers": {...} } }`. The app finds a colour by its role name wherever it sits under the groups (so groups are for people to read), and the older flat `"colours": {...}` still loads. It needs at least a valid `bg` and `text`; leave out any role (it is filled in). Saved themes are written in this shape.
- **Verified in the sim (2026-11-04):** the package's `themes/` files are read (`17 of 17 read`). A **new file** added to the installed folder is a **404 even if `index.json` names it**: the sim only serves files the package's `layout.json` lists (an edited `index.json` is served, so the contents of a listed file can be replaced).
- **Saved themes** (My colours tab, "Save theme"): the page cannot write files, and the files module (`wasm/files`) cannot write inside the package either (a probe on 5 Nov 2026 showed `Permission denied` for everything under `\pkg\`; `\work\` read, write and list all work; the probe has since been removed). So a saved theme is a `<theme-name>.json` file in the module's work folder, listed by the module at start-up (`PS.theme.loadSaved`), shown on the Themes tab as "saved: ...", deleted with "Delete <file>". The theme's id is `saved-<name>`; a file somebody drops in keeps its own id (and is renamed `<id>-saved` rather than replacing a preset). The folder is shown after saving (Microsoft Store install: `%LOCALAPPDATA%\Packages\Microsoft.Limitless_8wekyb3d8bbwe\LocalState\WASM\MSFS2024\push-planner\work`; Steam, from community reports and not checked: `%APPDATA%\Microsoft Flight Simulator 2024\WASM\MSFS2024\push-planner\work`). With no files module the theme goes to the app's own storage (8 slots, localStorage `pushplanner.themeslots`) instead.

- **Map style** (`src/ui/plot-draw.js`, `src/ui/theme.js`): line weights are part of a theme, `map.paths.*.width` and `map.labels` in the theme file (pixels; defaults 3, 6, 32, 15, 9). Saved themes include it. Named taxiways are drawn over unnamed paths, runways underneath; labels are bold, centred on their line, with a gap in the map background colour so the line stops short. Range rings are a Settings option (`rings`, default off); a scale bar is always drawn bottom left.
